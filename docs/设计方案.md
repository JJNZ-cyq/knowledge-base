## 1. 设计第一原则

### 1.1 三类资产必须分开存放

把所有东西塞进一个文件夹是这类项目最常见的死法。三类资产的**生命周期完全不同**：

| 资产 | 体量 | 变更频率 | 进 git？ | 存放位置 |
|---|---|---|---|---|
| 知识卡 / 笔记 | 小（KB） | 每天改 | ✅ 必须 | **库内**，纯文本 |
| 文献 PDF + 元数据 | 大（GB） | 只增不改 | ❌ 二进制 | **库外**，Zotero 托管 |
| 代码仓库 | 大（100 MB~GB） | 频繁 | ❌ 已有自己的 git | **库外**，`E:\repos` |
| 个人项目代码 | 中大 | 频繁 | ❌ 独立仓库 | **库外**，`E:\projects` |

**架构一句话：1 个纯文本大脑（可 git） + 3 个外部大仓库，用"指针"连接。**

### 1.2 库内只存"我自己的话"

收藏 ≠ 学会。判断一张卡是否合格，唯一标准是：**能不能用自己的话把它写出来**。
写不出来 → 标 `status: learning`，不许标 `status: mastered`。

### 1.3 结构落在元数据上，不落在文件名上

`frontmatter` 是未来一切自动化（看板、索引、AI 检索、复习排期）的地基。
**这一步偷懒，三个月后必然返工重写全部笔记。** 详见 §7。

## 4. 领域的具体设计

每个领域都有**独有的痛点**，不能用同一套模板。以下逐个给出：核心问题、子分区建议、推荐信息源、专属模板。

### 4.1 交能融合（领域 1 · 主战场）

**核心问题**：在交通网与配电网耦合的约束下，如何**调度能源**与**分配交通流**。

#### 当前重点：只建两个子区

> 决策：**先只建 `01-能量调度` 与 `02-交通流分配`**。其余子区（V2G、光储充、电氢、路域能源）统一放进 `09-其他\`，**不预建空目录**——未使用的结构一定是错的结构。后续上传的论文先进 `09-其他` 或直接进收件箱，攒够 3~5 篇再决定是否升格为独立子区。

**A. `01-能量调度`**

| 维度 | 覆盖内容 |
|---|---|
| 对象 | 微网 / 光储充站 / 服务区综合能源 / 电氢耦合系统 |
| 时间尺度 | 日前调度 → 日内滚动 → 实时控制 |
| 目标 | 经济性、低碳、寿命、可靠性、弃光率 |
| 手段 | 有序充电、需求响应、储能充放策略、多微网协同 |
| 难点 | 不确定性、多时间尺度耦合、通信与延迟、用户行为 |

**B. `02-交通流分配`**

| 维度 | 覆盖内容 |
|---|---|
| 经典模型 | UE 用户均衡、SO 系统最优、Wardrop 原理、Beckmann 变换 |
| 算法 | Frank-Wolfe、梯度投影、变分不等式、SUE 随机均衡 |
| 扩展 | 含充电的路径选择、动态交通分配（DTA）、多模式、出行需求预测 |
| 与电网耦合 | 交通流 → 充电负荷时空分布 → 配电网潮流（TN-PDN 的桥梁） |
| 数据 | OD 矩阵估计、手机信令、GPS 轨迹、路网 GIS |

> **A 与 B 的连接点**：交通流分配的输出是**充电负荷的时空分布**，它正是能量调度的输入。这个接口是整个交能融合的核心，建议单独维护一张常青卡 `10-交能融合\交通流→充电负荷→调度 的接口.md`，两张子区都链向它。

**暂缓（放入 `09-其他\`，攒够再升格）**：充电设施规划（存量 45 篇的主体，后续再迁）、V2G、光储充与微电网、电氢耦合、路域能源、耦合网络建模。

**信息源**：IEEE Xplore、Applied Energy、Energy Conversion and Management、Transportation Research Part B/C/E、eTransportation、Journal of Energy Storage；arXiv `eess.SY`。


**专属文献笔记模板追加字段**：
```yaml
problem: 选址 | 定容 | 调度 | 规划-运行联合 | 其他
method: MILP | MINLP | 双层 | 分布鲁棒 | 随机规划 | 启发式 | 强化学习
network: TN-PDN | 配电网 | 微网 | 交通网 | 单节点
solver: Gurobi | CPLEX | 自研
data: 真实城市 | 合成算例 | 标准测试系统
gap: 该文声称的贡献点（一句话）
```

### 4.2 大模型（领域 2）

**核心问题**：模型能力边界、如何使用、如何与自己的领域结合。

**子分区**：
| 子分区 | 内容 |
|---|---|
| A. 基础机制 | Transformer、注意力、训练目标、Scaling Law、位置编码 |
| B. 提示与推理 | 提示工程、CoT、上下文学习、RAG |
| C. 微调与对齐 | SFT、LoRA/QLoRA、RLHF/DPO、评测 |
| D. 智能体 | 工具调用、多智能体、规划、记忆 |
| E. 落地工程 | 部署、量化、推理加速、成本控制 |
| F. 与领域结合 | LLM 辅助优化建模、文献处理、代码生成 |

**专属特点**：这一领域**文献半衰期极短（3~6 个月）**，因此：
- 优先记**机制与原理**（不易过期），而非具体模型名与跑分（很快过期）；
- 每条"某模型能力上限"的结论必须写 **验证日期**，因为半年后可能就错了；
- 信息源以 arXiv、官方技术报告、HuggingFace 为主，期刊文献其次。

**专属字段**：
```yaml
claim: 该结论是什么
verified_at: 2026-09-23      # 所有能力性结论必须带日期
may_expire: true             # 标记易过期结论，复习时优先
```

### 4.3 编程与工程（领域 3 · C++ 与 Python 合并）

**合并的理由**：两者在本库里几乎总是同时出现（Python 建模 → C++ 加速内核），分开会让人反复在目录间横跳。合并后按**语言**分二级目录，不按语言分领域。

**核心问题**：从"能跑"到"知道为什么这样写"。

#### CPP 分区

| 分区 | 内容 | 记什么 |
|---|---|---|
| 语言特性 | 移动语义、模板/概念、SFINAE、并发、内存模型、UB | **什么规则 + 为什么有这条规则 + 违反会怎样** |
| 工程实践 | CMake、链接、调试（gdb）、sanitizer、性能剖析 | **症状 → 排查路径 → 根因** |
| 标准演进 | C++11/14/17/20/23 关键变化 | 时间线卡片 |

**独有机制 —— C++ 代码片段必须可运行**：
每张 C++ 知识卡末尾附一个**最小可编译片段**，存于 `90-附件\cpp-snippets\<卡名>.cpp`。
理由：C++ 的坑几乎都藏在细节里（生命周期、拷贝次数、UB），纯文字描述必然记错。

**坑清单**：单独维护 `12-编程与工程\CPP\坑清单.md`，一行一个"症状 → 原因"，检索价值极高。

#### Python 分区

| 分区 | 内容 |
|---|---|
| 语言与生态 | 类型标注、装饰器、生成器、异步、打包发布 |
| 科学计算 | numpy/pandas/scipy/matplotlib |
| 优化建模 | Gurobi / Pyomo / CVXPY ← **与交能融合、与 15-优化方法论 的接口** |
| 工程化 | 环境管理（uv）、测试（pytest）、项目结构 |

> **环境提示**：当前 Python 是 Anaconda 的 3.8.8，偏旧。建议在阶段 4 用已装好的 `uv` 建一个独立 3.12 环境专供本库脚本，避免与 Anaconda 全局环境互相污染。

#### 混合栈
`pybind11`、性能热点从 Python 下沉到 C++、调试跨语言栈。**这是"编程与工程"合并后新增的最大收益**——以前这个分区找不到归属。

**注意**：这个领域**不适用"文献笔记"结构**（没有论文可读）。它的知识来源是**代码、文档、踩坑**，所以卡片模板也不同：无 `problem/method/solver` 字段，改为 `symptom`（症状）与 `minimal_repro`（最小复现）。

### 4.4 19-交叉（路由规则已重写）

**v2 的规则有问题**：它把"Python×交能融合"这类内容也划进交叉区。但**用编程解决领域问题是领域内部的日常工作，不是交叉研究**——放交叉区会导致交能融合的子区被掏空。

**v3 路由规则（按顺序判断，第一个命中即定）：**

| 判断 | 归属 | 例子 |
|---|---|---|
| 只涉及 1 个领域？ | → 该领域目录 | "UE 用户均衡的 Wardrop 条件" → `10-交能融合\02-交通流分配\` |
| 是**用编程做领域的事**？ | → **领域目录**，加 `prog` 标签 | "Gurobi 建 TN-PDN 调度模型" → `10-交能融合\01-能量调度\` |
| 是**编程语言本身的特性**？ | → `12-编程与工程\` | "pybind11 返回 numpy 数组的所有权" → `12-编程与工程\混合栈\` |
| 是**方法论**，可跨领域复用？ | → `15-优化方法论\` | "双层规划的 KKT 转化条件"、Gurobi 调参 |
| **两个顶层领域相互增强**？ | → `19-交叉\` | "LLM 自动生成优化模型" → `大模型×交能融合\` |

**所以 `19-交叉` 只剩三种：**
```
大模型 × 交能融合    →  LLM 辅助优化建模、智能体调度、文献综述自动化
大模型 × 编程与工程  →  AI 辅助编程、代码生成与审查、自动化重构
三元交叉            →  三者同时涉及（如：LLM 生成 → Python 求解 → C++ 加速）
```

**通用纪律**：一张卡**只在一处存在**。若同时属于多处，选"最需要被找到"的那一处，其余位置用 `[[wikilink]]` 指过去，**绝不复制第二份**（否则必然分叉不一致）。

### 4.5 15-优化方法论（横切层）

**为什么独立**：你的文献里（双层、多目标、分布鲁棒、MILP）这些方法**反复出现在不同的应用场景中**，但知识本身与应用无关。独立成区后，学一次、处处可用。

| 分区 | 内容 |
|---|---|
| 建模范式 | LP / MILP / MINLP / 双层 / 多目标 / 随机规划 / 分布鲁棒 / 机会约束 |
| 求解与工具 | Gurobi、CPLEX、对偶与 KKT、线性化技巧、求解器调参 |
| 不确定性 | 场景生成与削减、鲁棒集构造、Wasserstein 球、样本外验证 |

**与领域区的双向链接约定**：
- 方法论卡 → 在 `used_in: []` 字段列出用到的领域卡
- 领域卡（文献笔记）→ `method` 字段填方法名，形成反向索引
- 这样"某个方法我到底在哪些问题上用过"可以一键查出，**这是本库最实用的查询之一**

## 5. 知识流动的四条核心工作流

### 5.1 收文献（目标：≤ 1 分钟）

```
① Zotero 浏览器插件（Zotero Connector）→ 网页点一下，元数据 + PDF 自动入库
② Better BibTeX 插件 → citekey 格式设为 authYearShortTitle（如 li2025evcharging）
③ 在 Zotero 里只维护两个层级：
     待读（未读的都在这里）
     已读（读完才移出来，按子分区建 collection）
④ 在 Obsidian 中用 Templater 新建文献笔记，自动填入 citekey + 元数据
⑤ 笔记 frontmatter 写 zotero: li2025evcharging —— 这是唯一的指针
```

**纪律**：Zotero 是"仓库"，Obsidian 是"加工厂"。**不在 Zotero 里做笔记**（Zotero 笔记无法被 git 版本化、无法双向链接、无法被 AI 批处理）。

### 5.2 收代码项目（目标：≤ 2 分钟）

```
① git clone <url> E:\repos\<name>
② 在 50-代码项目\<name>\ 建 速览.md，只记三件事：
     · 它解决什么问题（一句话）
     · 入口在哪（核心文件 + 关键函数）
     · 我打算怎么用 / 改它
③ frontmatter 记 repo: <url> @ <commit-hash>
④ 项目清单.md 里加一行
```

**纪律**：**永远不要克隆到知识库目录内**。库内进 git、源码也进 git → git 嵌套，几个月后必然出问题。
**版本锚点**：笔记里必须写 commit hash。否则半年后代码变了，笔记与源码对不上，等于废纸。

### 5.3 从"读过"到"学会"（最关键，也最容易被跳过）

```
  原文 / 文献 / 代码
        │  摘录、摘要 —— 这一步只值 20 分
        ▼
   文献卡（他人观点）
        │  用自己的话重写一个概念，一句话一张卡
        ▼
   知识卡（我的理解）  ★ 真正的产出在这里
        │  跨来源连接，形成可迁移的判断
        ▼
   永久卡（我的洞见）  ★ 复利来源于此
        ▲
        │  被解答
   问题卡（我的疑问）—— 驱动整个循环
```

**问题卡是引擎**：先有问题，再去找答案，比"读完一篇再想有什么用"效率高一个数量级。
每张问题卡的结构固定为：`问题描述 / 当前理解 / 假设 / 验证方式 / 结论`。

**四种卡的判据**（写不出来就是没到这一步，别硬写）：

| 卡型 | 合格判据 |
|---|---|
| 文献卡 | 能说清"作者主张什么 + 用什么方法证明 + 局限在哪" |
| 知识卡 | 能不看原文，用自己的话讲给别人听懂 |
| 永久卡 | 能与 ≥2 张别的卡建立非显然的关联 |
| 问题卡 | 问题足够具体，能设计出一个验证动作 |

### 5.4 每周维护（固定 30 分钟 · **周日**）

> 已定：固定在**周日**执行。固定下来才可能坚持，随缘维护等于不维护。

```
1. 清空 00-收件箱（15 min）—— 逐条处理：转卡 / 归入待读 / 直接删
2. 更新 docs\NOW.md（5 min）—— 只留 3 件事，写完就停
3. 跑体检脚本（2 min）—— 死链、孤立卡、缺 frontmatter、收件箱积压
4. 主动回忆抽查（8 min）—— 随机 5 张旧卡，遮住内容自述一遍，记不住就降级 status
5. git commit + push（1 min）—— 顺带完成异地备份
```

**唯一不可省略的动作是第 4 步。** 前三步是维护，第 4 步才是学习；第 5 步是保命。

## 6. Zotero 集成专章

### 6.1 必须装的插件

| 插件 | 作用 | 必要性 |
|---|---|---|
| **Better BibTeX (BBT)** | 稳定 citekey、导出 bib、自动更新 | ★ 必需，整个方案的地基 |
| Zotero Connector | 浏览器一键抓取元数据+PDF | ★ 必需 |
| ZotFile / Attanger | PDF 重命名与附件路径管理 | 推荐 |
| Jasminum | 中文文献元数据（知网/万方）| 视需要 |

### 6.2 citekey 规范（决定一切）

设 BBT 的 citekey 公式为：`auth.lower + year + shorttitle`，例：
```
li2025evcharging
wang2026tnpdn
chen2024v2gscheduling
```
**规范**：全小写、无空格、无特殊字符，不超过 24 字符。
理由：citekey 会出现在文件名、frontmatter、笔记正文、相互引用中，任何一次重命名都会引发连锁断链。

### 6.3 标签体系（受控词表，写在 `40-文献\标签体系.md`）

四级标签，用 `/` 分层：
```
领域标签   #dom/交能融合   #dom/大模型   #dom/cpp   #dom/python   #dom/交叉
类型标签   #type/综述  #type/方法  #type/算例  #type/工具  #type/观点
状态标签   #stat/待读  #stat/在读  #stat/已读  #stat/待复习  #stat/已掌握
主题标签   #top/选址定容  #top/双层规划  #top/V2G  #top/光储充 …
```
**纪律**：主题标签**只增不改**。需要新标签时先检查是否已有近义标签，避免出现 `#top/双层规划` 和 `#top/bilevel` 两套。

### 6.4 存量 102 篇的迁移方案

```
① 先在 Zotero 建好 collection 结构（对应 §4.1 的 A~G 七个分区）
② 批量导入：Zotero → 文件 → 导入 → 选择 E:\文献收集\充电相关\ 整个文件夹
     勾选 "将文件复制到 Zotero 存储目录"
③ 关键：这些 PDF 文件名已被截断（如 ..._2025_Applied.pdf），
     自动抓取的元数据质量可能很差 → 必须人工核对
④ 补救手段（按优先级）：
     a. 有 DOI 的：用 "通过标识符添加" 重新抓，元数据最准
     b. 无 DOI 的：从 PDF 首页文本 + Google Scholar 标题反查
     c. 都不行的：手工填 title/author/year/venue 四要素
⑤ 核对完成后才能生成 citekey —— 元数据错了，citekey 就是错的，
     基座一歪，后面全部笔记都要返工
⑥ 全部导入并核对后，将 E:\文献收集 改名归档为 E:\文献收集_已迁移，
     不要立刻删除，保留一个月的后悔期
```

**工作量预估**：102 篇 × 平均 1.5 分钟核对 = **约 2.5 小时**。这是全项目**最枯燥但不可跳过**的一步，建议分 4 次做完，不要一次硬扛。

### 6.5 备份

- Zotero 本体：用 Zotero 自带的**文件同步**（WebDAV 或官方存储）；
- `zotero.sqlite` 单独定期复制一份到云盘（数据库损坏是唯一会全盘丢失的风险）；
- **不要**把 Zotero 的 storage 目录放进 git。

## 7. 元数据规范（frontmatter）

### 7.1 通用字段

```yaml
---
title:      双层规划的 KKT 转化条件            # 必填
type:       知识卡                          # 必填：灵感|文献卡|知识卡|永久卡|问题卡|项目速览|周报
domain:     15-优化方法论                    # 必填：所属顶层领域目录名
subdomain:  建模范式                        # 选填：领域内二级目录名
tags:       [双层规划, KKT, MILP]            # 必填：受控词表，见 §6.3
status:     learning                       # 必填：inbox|learning|mastered|archived
created:    2026-09-23                     # 必填
updated:    2026-09-23                     # 脚本自动维护
source:     zotero:li2025evcharging         # 选填：zotero:|url:|repo:|book:
links:      ["[[20-永久卡/耦合约束的统一处理]]"]  # 选填：显式关联
confidence: 3                              # 选填：1-5，我对这条结论的把握
reviewed:   2026-09-23                     # 选填：上次主动回忆日期
---
```

**`domain` 的合法取值（受控，只有 6 个）**：
```
10-交能融合 | 11-大模型 | 12-编程与工程 | 15-优化方法论 | 19-交叉 | 20-永久卡
```
> `subdomain` 只在领域内有二级目录时填写，如 `01-能量调度` / `02-交通流分配` / `建模范式`。
> 它存在的意义：`domain` 太粗（整个交能融合），`tags` 太散（自由生长），`subdomain` 恰好是"我当前在攻哪一块"。

### 7.2 分类型追加字段

| 类型 | 追加字段 |
|---|---|
| 文献卡（领域类） | `problem` / `method` / `network` / `solver` / `data` / `gap`（见 §4.1） |
| 文献卡（编程类不适用） | 编程与工程领域无文献卡，改用下方"踩坑卡" |
| **踩坑卡（编程专用）** | `symptom`（症状）/ `cause`（根因）/ `minimal_repro`（最小复现路径或片段文件） |
| 知识卡 | `prereq: []`（前置知识）、`used_in: []`（我在哪用过） |
| 永久卡 | `derived_from: []`（由哪些卡综合而来） |
| 问题卡 | `hypothesis` / `verify_by` / `conclusion` / `closed_at` |
| 项目速览 | `repo` / `commit` / `stack` / `my_use` |
| 大模型类卡 | `claim` / `verified_at` / `may_expire`（见 §4.2） |
| **方法论卡（15-区专用）** | `used_in: []`（在哪些领域卡里用过——反向索引的关键，见 §4.5） |

### 7.3 命名规范

```
日常卡片：   <简短标题>.md                  例：双层规划的KKT转化.md
日期型：     YYYY-MM-DD-<标题>.md           例：2026-09-23-读TN-PDN联合优化.md
文献笔记：   <citekey>.md                   例：li2025evcharging.md  ← 用 citekey，不改名
周报：       YYYY-Www.md                    例：2026-W39.md
```
**禁止**：文件名里出现 `空格 / \ : * ? " < > |`、超过 60 字符、用"新建文档""未命名"。

### 7.4 为什么值得这么麻烦

frontmatter 是**唯一能让笔记从"文本"变成"数据"的东西**。有了它：
- Dataview 插件 → 自动生成看板："所有 status=learning 且 domain=大模型 的卡"
- 脚本 → 自动生成索引、MOC、断链报告
- AI → 可以按字段筛选后批量投喂，而不是全文硬塞
- 未来接复习系统 → 直接按 `status` + `reviewed` 排期

**没有 frontmatter，以上全部做不了，且无法事后补救。**

## 8. 自动化脚本层

**技术选型**：Node.js（`.mjs`，零第三方依赖）。
理由：本机 Node 24.16 很新且干净；Python 3.8.8 是 Anaconda 的、偏旧且易被环境污染；纯 Node 脚本不需要 npm install，长期不会因为依赖腐烂而失效。

| 脚本 | 功能 | 阶段 |
|---|---|---|
| `tools/new.mjs` | 按模板新建任意类型卡片，自动填 frontmatter | 1 |
| `tools/check.mjs` | 体检：断链、孤立卡、frontmatter 缺失、收件箱积压天数 | 1 |
| `tools/sync-moc.mjs` | 自动生成各领域 `_MOC.md` 与 `40-文献\索引.md` | 3 |
| `tools/ingest.mjs` | 输入 URL / arXiv id / GitHub 链接 → 自动抓元数据生成草稿卡 | 3 |
| `tools/review.mjs` | 取出今天该复习的卡，生成复习清单 | 5 |
| `tools/pack.ps1` | 打包备份（含附件）、校验、上传云盘 | 2 |
| `tools/setup.ps1` | 换机还原：装工具、clone 库、提示 Zotero 配置 | 2 |

**设计约定**：
- 所有脚本**只读不写**破坏性操作，除了 `new.mjs` 创建新文件；
- `check.mjs` 是唯一的"质量守门人"，应作为每周维护的固定动作；
- 脚本本身**入 git**，与笔记一起版本化。

### 8.1 git 与远端备份（已定：建私有远端）

**为什么必须建远端**：本地 git 只解决"改坏了能回滚"，**不解决硬盘坏掉**。知识库的价值随时间是复利增长的，丢一次等于归零。

**配置**：

```
本地仓库：  E:\知识学习                      （git init，main 分支）
远端仓库：  GitHub 私有库 knowledge-base      （已配好，见下）
实际地址：  https://github.com/JJNZ-cyq/knowledge-base.git
```

> **用户名注意**：GitHub 账号是 **`JJNZ-cyq`**，不是 `jjnz`。
> 本机 git 的 `user.name` 恰好也叫 `jjnz`，极易混淆——**以凭据管理器里的账号为准**。

> **仓库名用英文**：本机路径含中文，为避免跨平台/命令行编码问题，远端名不跟路径名走。

**`.gitignore` 必备条目**（防止仓库被二进制撑爆）：
```gitignore
# 大文件绝不入库
90-附件/**/*.pdf
90-附件/**/*.zip
90-附件/**/*.mp4
*.pdf
*.zip

# 临时与系统文件
.obsidian/workspace.json
.obsidian/workspace-mobile.json
.trash/
.DS_Store
Thumbs.db
~$*
```

**三处需要 git 的地方，务必分清**（这是最容易搞混的一节）：

| 位置 | 是 git 仓库吗 | 备份方式 |
|---|---|---|
| `E:\知识学习` | ✅ 本库 | push 到 GitHub 私有库 |
| `E:\repos\*` | ✅ 但**是别人的仓库** | 不用管，随时可重新 clone |
| `E:\projects\*` | ✅ **你自己的代码** | 各自独立建远端（不要并进知识库） |
| `C:\Users\CYQ\Zotero` | ❌ **禁止 git** | Zotero 官方同步 + `zotero.sqlite` 定期复制 |
| `E:\知识学习\90-附件` | ⚠️ 在库内但不入库 | 随附件靠云盘同步 |

**关于网络（两次实测，结论已变）**：

| 时间 | Agent 沙箱模式 | TLS 出站 | 结果 |
|---|---|---|---|
| 2026-09-23 | workspace-write | ❌ 被禁 | `schannel: SEC_E_NO_CREDENTIALS (0x8009030e)` |
| 2026-09-24 | **full-access** | ✅ 放开 | `git push` 成功 |

**结论：网络权限取决于会话的文件策略，不是固定不变的。**
- 沙箱受限时，push 需你在自己终端执行；权限放开后 Agent 可直接推送。
- 无论哪种情况，**你在自己终端里跑 `tools\push.cmd` 始终可用**。

**执行策略坑（Windows 必踩）**：本机 PowerShell 各作用域均为 `Undefined`，
客户端默认为 `Restricted`，直接运行 `.ps1` 会报"因为在此系统上禁止运行脚本"。
因此推送统一用 **`tools\push.cmd`**（内部带 `-ExecutionPolicy Bypass`），
**无需修改系统安全设置**。同理，`.cmd` 文件必须**纯 ASCII** —— cmd.exe 按
OEM 代码页(936)解析，中文注释会被当成命令执行（已实测踩到）。

若 push 报 `non-fast-forward`，说明远端有你本地没有的提交，
**先 `git pull --rebase origin main` 再推，不要强推**。

## 10. 明确不做的事（防过度设计）

| 不做 | 原因 |
|---|---|
| ❌ 一开始就上向量数据库 / RAG | 卡片 < 1000 张时，grep 更快、更准、零维护 |
| ❌ 自建 Web 界面 / 数据库 | Obsidian + 文件系统已经够用，自建必然烂尾 |
| ❌ 把所有 PDF 放进库 | git 会在几个月内变得又慢又不可用 |
| ❌ 追求完美的目录分类 | 分类会变，frontmatter 不会。**先记下来，分类后置** |
| ❌ 用文件夹层级表达"知识关系" | 关系用 `[[wikilink]]`，文件夹只表达"归属" |
| ❌ 一次性搭完 | 你的节奏要求就是渐进，且未使用的结构一定是错的结构 |
| ❌ 收藏夹式囤积 | 收件箱必须每周清空，否则库会变成垃圾场 |

## 11. 风险与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| **收件箱永不清理** | 库退化为收藏夹 | 每周固定 15 分钟；收件箱超 20 条即告警 |
| **只收藏不写作** | 学不会，项目失去意义 | §5.3 的四类卡判据；每周抽查 5 张 |
| Zotero 元数据脏 | citekey 全错，笔记基座报废 | §6.4 强制人工核对，宁慢不错 |
| 二进制混入 git | 仓库膨胀、clone 变慢 | `.gitignore` 硬性排除 `90-附件` 大文件 |
| 目录设计过度 | 记笔记前的心理成本过高 | 顶层固定 3 领域 + 交叉 + 方法论 + 归档，不再加层级 |
| 大模型领域知识过期 | 笔记变错误 | §4.2 的 `verified_at` + `may_expire` 机制 |
| Python 环境污染 | 脚本时好时坏 | 阶段 4 用 `uv` 建独立环境 |
| 换机后指针全断 | 笔记里的 citekey 找不到 PDF | `setup.ps1` + Zotero 官方同步 |
| **交能融合摊子铺太大** | 什么都学、什么都没学深 | §4.1 只开两个子区，其余进 `09-其他`，**攒够 3~5 篇再升格** |
| **库与 Zotero 状态脱节** | 笔记里的 citekey 在 Zotero 查无此文 | 每周维护时跑一次 citation 校验；删文献前先查引用 |
